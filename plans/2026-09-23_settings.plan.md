# Settings the machine remembers, instead of a URL it has to be launched with

## Context

`?view=`, `?relief=` and `?lod=` accumulated as deep links, and `?lod=full` — added this
morning — is the first one somebody has to actually *use* on the day. A URL parameter is a
poor control surface for an installation: it has to be retyped after any navigation, it is
invisible once set, and "what is this machine currently configured to do?" has no answer except
reading the address bar.

The exhibition opens **24 Sep, tomorrow**, on three surfaces — visitors' phones via QR, a
projection, and a laptop. The laptop and the projector are set up once and left; the phones
must be untouched by any of it.

## Goal

A `/settings` page where the machine is configured — opening view, topography style, level of
detail, language — that persists in `localStorage` and survives reloads and restarts. The
viewer reads it at startup. Visitors' phones are unaffected, because they have nothing stored.
URL parameters keep working and still win, so a QR code can still point at a view.

## Approach

**`localStorage`, because there is no server.** `output: 'export'` means settings cannot live
anywhere else. That is a genuine fit rather than a compromise: settings are *per machine*, and
per machine is exactly what a kiosk wants. The laptop keeps its configuration; a visitor's
phone has none and gets the defaults.

**Precedence: URL parameter > stored setting > default.** A parameter is an explicit, one-off
instruction and must beat a remembered one, or a QR code aimed at the valley would be silently
overridden by whatever the machine was last set to. Keeping the parameters also keeps the
documented QR capability — `?view=` exists so a code can land somebody somewhere specific.

**Reading happens in an effect, never during render.** The page is prerendered by the static
export, so touching `localStorage` during render is a hydration mismatch. The existing
URL-parameter effect is already the right shape and this joins it.

**Every read and write is wrapped in try/catch and every stored value is re-validated.**
Storage throws in private mode and returns whatever was last written, which may be from an
older build. A settings blob that fails to parse must fall back to defaults rather than blank
the exhibition. `parseSettings` is pure and tested, and an unknown view or relief style is
dropped rather than trusted.

**The page is not linked from the viewer's control row.** The visitor-facing controls are the
three views and the language; a rendering-quality switch beside them would be the first control
in the piece that is about the software rather than about Wat Ket. It is reachable by typing
`/settings`, and from the debug overlay, which is where an operator already goes.

**`f` stays.** Settings are for configuring; `f` is for judging full geometry on the machine
without a round trip through another page.

### Rejected

- **A panel inside the viewer.** It would have to live in the topbar to be reachable, which is
  the row this is trying to stay out of.
- **Dropping the URL parameters.** `?view=` is how a QR code aims at a view; that is a shipped
  capability and settings are not a replacement for it.
- **Putting settings in the scene document.** The document describes Wat Ket. What one laptop
  in one mall is configured to do is not a property of Wat Ket.
- **A cookie, or a query string the viewer rewrites.** Storage is the thing that survives a
  restart without a server.

## Keyboard interaction

1. **Tab order** — through the four groups in the order above, then "Open the viewer", then
   "Reset to defaults". Radio groups are single tab stops with arrow keys inside them, which is
   what a native `input[type=radio]` with a shared `name` gives for free.
2. **Shortcuts** — none on this page. In the viewer, `f` still toggles detail and now writes
   the setting, so what staff toggled is what the machine remembers.
3. **Focus management** — changing a radio saves immediately and moves no focus. "Reset to
   defaults" returns focus to the first radio group.

## Verification

1. `npm run dev`, open `/settings`. Nothing stored, defaults selected.
2. Choose "Every building as geometry", then "Open the viewer". It loads full geometry
   without any parameter in the URL.
3. Reload `/`. Still full geometry — the machine remembered.
4. Open `/?lod=near`. The parameter wins for that load; `/settings` still shows `full` stored.
5. Press `f` in the viewer, return to `/settings` — the stored value followed the toggle.
6. "Reset to defaults", reload `/` — back to the raster.
7. In a private window, `/settings` still renders and still lets the session be changed.
8. `npm run build` — three routes, and `/` still fetches 3.2 MB on a default load.

## Outcome

Done 23 Sep 2026. `/settings` is the fourth route, and `?lod=full` is no longer something the
machine has to be launched with.

Verified against the **static export** rather than the dev server, because the export is what
the exhibition laptop runs and the two behave differently:

| | default (nothing stored) | configured `lod=full` |
|---|---|---|
| bytes fetched | **4.89 MB** | 13.8 MB |
| `load` event | under a second | 5.1 s |
| then | — | ~6 s of frozen main thread while it merges |

The phone case is the one that had to hold and it does: with nothing stored, a plain `/` load
fetches 4.89 MB and the 19 MB document is never requested. The configured path is a good deal
cheaper than the 26 s measured in dev this morning — that number was Turbopack serving 19 MB of
unminified JSON, not what the laptop will do.

The whole loop was checked end to end: the page saves on change; the viewer reads stored view,
relief, detail and language at startup; `?lod=near&view=valley` overrides both **without**
rewriting what is stored; `f` in the viewer writes its toggle back and leaves the other three
fields alone; Reset clears storage, restores the defaults in the form and returns focus to the
first group.

Two things worth keeping:

**An absent URL parameter must not clobber a stored setting**, and that is the single test most
worth having here. The naive `resolveSettings` — read every parameter, fall back to a default —
would mean that merely opening `/` wipes the machine's configuration, which would make settings
strictly worse than the parameters they replace.

**`f` had to start saving.** A toggle that forgets is worse than no toggle: the machine would
look configured, and come back wrong after a restart. It writes the whole settings object back
rather than just its own field, so it cannot drop the other three.

Cut during implementation: `hasViewParam`, which was written, exported and tested before it had
a caller — a stored view and a parameter view turn out to mean exactly the same thing to the
on-ramp. Deleted rather than left as an abstraction waiting for a use, which is the rule in
CLAUDE.md.
